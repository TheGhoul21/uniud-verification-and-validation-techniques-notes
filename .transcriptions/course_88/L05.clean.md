In particular, we introduced the emptiness problem, which may seem like a trivial or even meaningless problem: the problem of establishing whether the language recognized by a given automaton is empty or not. One might ask, why would we even build an automaton that recognizes the empty language? But this is not as trivial as it seems. If, for a moment, we think of an automaton as a particular way of expressing a logical formula — which is in fact the case, as we'll see later in the course — then checking whether the language recognized by the automaton is empty is equivalent to the logical problem of establishing whether the formula is satisfiable, meaning whether it has at least one model that makes it true. Once we establish this correspondence between the words belonging to the language of the automaton and the models of the formula, the emptiness problem becomes, in logical terms, the satisfiability problem.

If we want to talk about satisfiability from the perspective of verification, satisfiability is the consistency problem. We want to guarantee that the formula we write is consistent — that it admits at least one model. This is a very important problem, because if you use formulas to specify the expected behavior of a system or a program, checking that what you write is consistent makes sense: it's a fundamental, sanity-check kind of problem — in the literature it's literally called that, a sanity check. We want to be sure that what we write is what we mean, and the first condition is that it must be satisfiable — it must be consistent, it must not contain any contradiction that makes the formula unsatisfiable. So the emptiness problem is a fundamental problem, and despite appearances, it's not trivial. It's the basic problem.

The other important point is that other problems can be reduced to this one. In particular, there's a very important problem called the inclusion problem — the problem of checking whether a given language is included in another. This is a classical problem, and in the verification setting, the name usually given to it is model checking. Model checking is the main problem in verification. Why is the inclusion problem the model checking problem? Because if you consider one language as describing the possible behaviors of a system, and another language as describing all the models of a formula that specifies an expected property of the system, then checking this inclusion amounts to checking whether the behaviors of the system satisfy the specified property — which is exactly the verification problem. We want to define a number of expected properties and automatically check that our system satisfies them. That's formal verification.

This problem — checking whether one language is included in another — is equivalent to checking that L1 intersected with the complement of L2 is equal to the empty set, which is the emptiness problem. So we can rewrite the inclusion problem as an emptiness problem, about the original language L1, the complement of L2, and their intersection. Now we can define Büchi automata — named after Büchi, who introduced them. A Büchi automaton is a tuple, and we use the usual notation: a calligraphic A with five components. Q is a finite set of states, A is the finite alphabet, delta is the transition relation — and I write delta because we're talking about non-deterministic automata, since Büchi automata as we're introducing them are non-deterministic — Q zero is the initial state, a state in Q, and we assume there's just one initial state, and F is the set of final states, a subset of Q, as usual. Delta is a subset of Q by A by Q, and the meaning is the usual one: if I'm in state q and I read symbol a, I can go to state q prime, and since this is a relation, we can have triples that share the same first two components but different third components, meaning that from a given state, reading a given symbol, we can move to several different states — non-determinism.

Now we define a computation of a Büchi automaton on an omega-word — this too is standard. A computation of calligraphic A over an omega-word alpha is itself an omega-word, but over Q rather than over the alphabet: an infinite sequence of states, sigma, such that two conditions hold, the usual ones. First, the computation starts from the initial state: sigma zero equals Q zero. Second, moving from one state to the next while reading a given symbol must be justified by a transition in delta: for all positions i greater than or equal to zero, the triple sigma i, alpha i, sigma i plus one must belong to delta. The only new point here is that the computation must go on forever, because the input word is infinite, and so the computation must also be infinite.

Now, the key point. Since the automaton is non-deterministic, in general, given an omega-word, there may be infinitely many different computations — exactly as with non-deterministic finite automata. As we did there, we say a word is accepted if at least one of its possible computations is successful — that rule stays the same — but we need something more, because we can't say a computation is successful once it reaches a final state; there's no "once" here. So we need a different criterion. Note this isn't the only possible choice — it's the choice Büchi made for his automata, and we'll see other kinds of automata with different acceptance criteria — but Büchi's choice is the following: a computation sigma is successful if the set of states it passes through infinitely many times, In of sigma, intersected with the set of final states, is different from the empty set. In other words, if there exists at least one final state that the computation passes through infinitely many times, the word is accepted. That's Büchi's criterion. I repeat, it's not the only possible one, but it's a fairly natural one — it's not a very demanding condition, because we don't care about the other states, whether we pass through them finitely or infinitely many times; we only need at least one final state to be visited infinitely often.
